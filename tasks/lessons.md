# 教訓・トラブルシューティング (`tasks/lessons.md`)

## 1. SwiftBar / xbar のプラグイン読み込み不具合

### 事象
`brew install --cask swiftbar` による自動インストール後、単に `open -a SwiftBar` で起動するだけでは、メニューバーにプラグインが表示されず「SwiftBar」という文字だけが表示され、裏でプラグインディレクトリ選択画面（またはルート `/` を指した状態）で待機してしまう。

### 原因
SwiftBar の初回起動時のデフォルト設定（plist）で、`PluginDirectory` が `/` や未設定になっており、我々が作成した `~/Library/Application Support/SwiftBar/plugins/` を自動認識せずにロードを停止していた。

### 対策・解決手順
`defaults` コマンドを使用して、plist に直接正しいプラグインパスを書き込み、アプリを強制再起動することでダイアログなしで一撃ロードさせることが可能。

```bash
# 1. plistにプラグインディレクトリを直接書き込む
defaults write com.ameba.SwiftBar PluginDirectory "/Users/user/Library/Application Support/SwiftBar/plugins"

# 2. アプリケーションを再起動する
killall SwiftBar
sleep 1
open -a SwiftBar
```

### 教訓
macOS のメニューバーユーティリティを自動導入・設定する場合、単純にアプリを起動するだけでなく、`defaults` や設定ファイル（`.plist`等）を直接パース・修正して初期ダイアログや選択手順をバイパスしてあげることが、シームレスな「一撃導入」には極めて重要である。

## 2. macOS GUIアプリ実行環境における環境変数（PATH）問題

### 事象
ターミナル上の手動実行では正常に `node` を呼び出せていたスクリプトが、SwiftBar などの GUI アプリケーションからバックグラウンド実行された際、外部コマンド（`node` 等）の呼び出しに失敗してフォールバック動作になってしまっていた。

### 原因
macOS の GUI アプリから起動されるプロセスの環境変数（特に `$PATH`）は、ユーザーのシェル（`.zshrc` 等）の設定を引き継がず、最小限のシステムパス（`/usr/bin:/bin` 等）のみになる。そのため、Homebrew 等でインストールした `/opt/homebrew/bin/node` へのパスが通らず、コマンドが実行できなかった。

### 対策
Python スクリプト等の外部プロセス起動ロジックにおいて、直接バイナリ名（`node`）で呼ぶのではなく、以下の絶対パス自動検出ヘルパーを実装して絶対パスで呼び出すようにする。

```python
def get_node_path():
    paths = [
        "/opt/homebrew/bin/node",
        "/usr/local/bin/node",
        "/usr/bin/node"
    ]
    for p in paths:
        if os.path.exists(p):
            return p
    return "node"
```

### 教訓
GUI 拡張機能やメニューバープラグインなどで、外部のランタイム（Node.js, Python, CLIツール等）をサブプロセスとして起動する際は、絶対に環境変数（PATH）を前提とした設計にしてはならない。必ず想定される絶対パスを自動検出するか、フルパスで呼び出す仕組みを徹底する必要がある。

## 3. SPA（React）の動的画面におけるアニメーション・ローディングの待機問題

### 事象
CDP（Chrome DevTools Protocol）経由で設定モーダルを開き、Modelsタブへクリック遷移した直後にDOMを取得すると、ゲージの目盛りセグメントが描画途中（またはローディング中）のため、すべて0%（非点灯）または誤ったデフォルト値としてスクレイピングされてしまう。

### 原因
シングルページアプリケーション（SPA）では、モーダルの展開アニメーションやAPIからのデータフェッチおよび再描画に数百ミリ秒から数秒のラグが存在する。直後の評価（evaluate）はロード前の一時的なDOMや0%の過渡期状態を拾ってしまうため。

### 対策
- モーダルクリックやタブ切り替えなどのトリガー操作ごとに、十分なアニメーション・描画完了ディレイ（設定オープンに `1.0秒`、モデル切り替えに `1.5秒` 等）を明示的に挟む。
- 単純なテキストパースだけでなく、行コンテナのDOM配下にあるセグメント要素の `style` 属性における `width: 100%` を厳密に走査・カウントする多重構造のフォールバック付きロジックを実装する。
- サブプロセスのタイムアウト値（Python側の `timeout`）を十分な長さ（10秒程度）に延長し、SPAの描画遅延による異常終了を防止する。

### 教訓
動的SPAや複雑なReactアプリケーションのUIをバックグラウンド操作（CDP等）でスクレイピングする際は、必ずアニメーションとAPIフェッチに伴う時間差を考慮した適切なシーケンス制御（段階的なディレイ）を徹底しなければならない。また、過渡的な状態を誤検知しないよう、DOMの属性（`style` の幅など）を厳密にスキャンする走査アルゴリズムの二重の防護設計が必要不可欠である。

## 4. SwiftBar / xbar の予約文字（デリミタ）との干渉問題

### 事象
メニューバーのタイトル文字列に ` | `（半角の縦棒）を使用すると、最初の `|` より後ろのモデル項目がすべてカットされ、最初のモデル（`F-Med:🟢`）しか表示されなくなってしまう。

### 原因
SwiftBar および xbar フォーマットにおいて、`|` は「タイトル文字列」と「パラメータ項目（フォントや色など）」を区切るためのシステム予約文字であるため。タイトル内に `|` を含めると、最初の `|` 以降がすべてパラメータオプションとして解釈されてしまい、タイトルから削除されてしまう。

### 対策
メニューバータイトルを結合する際の区切り文字に `|` ではなく、システムと干渉しない安全な記号「`  •  `」（半角スペース2つ＋バレット記号＋半角スペース2つ）や「`  `」（スペース複数）などを使用する。

### 教訓
外部ツールの標準出力インターフェース（特にSwiftBarやxbar等）にテキストを渡す際は、そのパーサー仕様を厳密に把握し、予約デリミタ（`|` など）との意図しない競合を防ぐために、代替の安全な文字（バレット記号等）を選択するかエスケープ処理を必ず徹底すること。

## 5. シンボリックリンク配置スクリプトにおけるカレントディレクトリ解決問題

### 事象
ターミナル上の直起動では正常にクォータ情報（%表示）がリアルタイム同期できていたが、SwiftBar 経由でバックグラウンド実行された際、常にキャッシュ表示のフォールバック動作になってしまっていた。

### 原因
SwiftBar のプラグインディレクトリには、スクリプトへのシンボリックリンクが配置されている。Pythonスクリプト内で `os.path.abspath(__file__)` を使用してカレントディレクトリを解決すると、シンボリックリンクが置かれている場所（`~/Library/Application Support/SwiftBar/plugins/`）が基準となり、隣にあるはずの `get_quota.js` を見つけられず、スクレイピング実行に失敗していた。

### 対策
スクリプトの位置を特定する際は、`os.path.abspath(__file__)` ではなく `os.path.realpath(__file__)` を使用し、シンボリックリンクを自動的に実体パスへ解決してからディレクトリ名を特定する。
`SCRIPT_DIR = os.path.dirname(os.path.realpath(__file__))`

### 教訓
OSの拡張機能やタスクスケジューラなどで、シンボリックリンク経由で実行される可能性のあるスクリプトを開発する際は、絶対に `abspath` を使ってはならない。必ず `realpath` を用いてリンクの実体パスを解決した上で相対ファイル参照を行う設計を徹底すること。

## 6. SwiftBar プラグインメタデータの欠落による [?] 警告プレースホルダーの発生

### 事象
メニューバーのプラグイン表示の左端に、無効な警告プレースホルダー `[?]` マークが表示されていた。

### 原因
SwiftBarの公式仕様に準拠したメタデータがスクリプト内に記述されていなかったため、アプリ側でプラグインのアイコンや情報が欠損していると判定され、警告プレースホルダーが出力されていた。

### 対策
スクリプトの先頭（シバン行の直後）に、`<swiftbar.title>` や `<swiftbar.icon>` などの公式メタデータタグを含むコメントブロックを追加する。

### 教訓
外部の統合ランチャー（SwiftBar, xbar, Alfred, Raycast等）向けに拡張機能を開発する際は、単に標準出力をフォーマットするだけでなく、そのプラットフォームが要求するメタデータ定義（ヘッダー記述など）を最初から完璧に満たしておくこと。これにより、プレースホルダーや読み込み警告を未然に防ぐことができる。

## 7. 自動GUI操作スクリプトの実行頻度とユーザー体験の競合（ウィンドウポップアップ干渉）

### 事象
メニューバーの更新周期（30秒）に合わせて毎回ブラウザの設定モーダルが目の前で自動開閉してしまい、ユーザーのタイピング作業を著しく妨げていた。

### 原因
正確なモデルクォータをDOMから取得するために、30秒に1回CDP（Runtime.evaluate）経由で設定モーダル（Settings > Models）の自動開閉処理を同期的に走らせていたため。

### 対策
- **スマートキャッシュ制御（Bypass）の導入**:
  - `quota_cache.json` に最新フェッチ日時を記録し、前回のフェッチから **15分** 経過していない場合はCDP操作を完全にスキップさせ、キャッシュから **0.04秒** で超高速出力する。
  - 平常時の自動更新では目の前で設定ウィンドウは一切開かないように制御。
- **強制更新トリガーの統合**:
  - メニュー内の「🔄 再読み込み」をクリックした時に限り、SwiftBarの `bash` オプション経由で `--force` 引数を与えてスクリプトを再起動させ、その場でのみ強制的にリアルタイム同期を実行する。

### 教訓
CDPなどのブラウザ自動操作は非常に強力だが、ユーザーがアクティブに操作している対話ブラウザと同じコンテキストで動作する場合、頻繁な自動操作は深刻なユーザー体験の干渉（ウィンドウのポップアップ等）を引き起こす。
このようなケースでは、**「平常時は超高速なキャッシュ表示（無干渉動作）」に徹し、重い・干渉する自動操作は「低頻度（15分や30分に1回）のバックグラウンド実行」や「ユーザーが明示的にRefreshをクリックした時」にのみ限定するスマートキャッシュ設計**を徹底しなければならない。


## 8. LSPのConnect API直接フェッチへの刷新による画面非干渉化

### 事象
ブラウザ自動操作（CDP経由のモーダル開閉）では、キャッシュ時間を15分に引き延ばしても、初回起動時や強制同期時にどうしても一瞬ウィンドウが開閉してしまい、プロ仕様のツールとして美しさに欠けていた。

### 原因
設定画面のDOMからしかクォータ残量を取得できないと思い込んでいたため、ブラウザ操作（設定ボタンクリック -> Modelsタブ遷移 -> DOM解析 -> モーダルクローズ）を余儀なくされていた。

### 対策
- 常駐している `language_server` プロセスを `ps aux` から特定し、引数の `--csrf_token` からCSRFトークンを抽出。
- `lsof -i` から該当PIDがLISTENしているローカルAPIポートを自動特定。
- `/exa.language_server_pb.LanguageServerService/GetUserStatus` に対して、HTTP POSTで直接Connect APIリクエストを送信。
- 画面開閉は1ミリも発生させず、完全に無音・バックグラウンドで100%正確なモデルクォータを取得することに成功。API呼出が非常に軽量なため、キャッシュ時間（以前は15分）を `0秒` に設定し、毎回の更新で完全リアルタイム同期が可能に。

### 教訓
画面上のDOMをスクレイピングする原始的なアプローチをとる前に、対象プロダクトのバックグラウンドプロセス（Language Serverなど）が提供するローカルAPIやソケットが存在しないかを深く調査し、リバースエンジニアリングや直接通信によるハックを検討すること。これにより、ユーザー体験（UX）を損なわない完全にクリーンでプロ仕様のツールを構築できる。

## 9. SwiftBarプラグインディレクトリ内の不要なデータ・キャッシュファイル誤認識による [?] エラー問題

### 事象
メニューバーのクォータ情報は正常に表示されているにもかかわらず、その右隣にクエスチョンマーク付きの警告アイコン `[?]`（プラグインエラー）が表示されてしまっていた。

### 原因
キャッシュファイル `quota_cache.json` が、スクリプトと同階層（`SCRIPT_DIR` 即ち SwiftBarの `PluginDirectory`）に作成されていた。
SwiftBarはプラグインディレクトリにあるすべてのファイルをプラグイン（スクリプト）としてロード・実行しようとするため、JSONファイルである `quota_cache.json` を実行してエラー（例外）を吐き出し、それがメニューバー上の `[?]` 警告エラー表示を引き起こしていた。

### 対策
- キャッシュファイルの保存パスを、プラグインディレクトリの外（例：`~/.gemini/antigravity/quota_cache.json`）に変更する。
  `QUOTA_CACHE_FILE = os.path.expanduser("~/.gemini/antigravity/quota_cache.json")`
- プラグインディレクトリ内に生成されてしまっていた不要な `quota_cache.json` をコマンド `rm` で完全に削除する。
- SwiftBarを再起動し、誤認識プラグインを排除する。

### 教訓
SwiftBarやxbarなどのプラグインディレクトリは、**実行可能なスクリプトファイルのみを配置する純粋なディレクトリ**として保つ必要がある。スクリプトが作成するデータ、キャッシュ、一時ファイル、アセットなどの不要なファイルは、絶対に同ディレクトリ内に書き出してはならない。必ずホームディレクトリ下のアプリデータ領域や一時ディレクトリ（`/tmp` 等）を指定し、プラグインディレクトリのクリーンさを維持すること。

## 10. 多段階（グラデーション）カラーと絵文字マッピングによる視認性と高級感の向上

### 事象
各モデルのクォータ残量表示について、単なる3段階（🟢, 🟡, 🔴）の分類から、ユーザー指定による6段階の微細なグラデーション（🟣 100% / 🔵 80% / 🟢 60% / 🟡 40% / 🟠 20% / 🔴 0%）へ表現形式を刷新。

### 対策
- `get_quota_emoji` 関数にて、100% (🟣) およびそれ以下の80%, 60%, 40%, 20%, 0%の各閾値を詳細に判定し、それぞれに適した絵文字をマッピング。
- 同時に `get_quota_color` 関数を導入し、SwiftBarのドロップダウン詳細行のフォントカラー（Hex）を上記の絵文字カラーと同調する美しい色彩（紫、青、緑、黄、橙、赤）に統一した。
- 当初は100%（満タン）状態の数値をあえて省略し `🟣` 単体としていたが、すべてのモデルが同じ表記フォーマット（例：`Sonnet:🟣100%`）で統一されている方が情報の一貫性と視認性が高く、ユーザーにとって直感的であるため、100%の時も `🟣100%` とパーセンテージを明記する仕様へアップデートした。

### 教訓
- メニューバーのように表示領域が限られたUIであっても、**「すべての項目で同一の表示ルール（絵文字＋数値％）を徹底すること（一貫性）」**が、ユーザーの視覚的な混乱を防ぎ、一目で全ての状態を美しく比較するために極めて重要である。
- また、絵文字とテキスト色を同期させることで、「高級感・プレミアム感」が劇的に向上し、プロダクトとしての品質がワンランク上がる。
- テストコードの構築においては、具体的な絵文字や色などの「デザイン表現」に依存せず、部分文字列の存在チェック（`assertIn` など）を活用した柔軟なアサーション設計をしておくことで、表示カスタマイズ時にテストが壊れず安全にアップデートできる。

## 11. SwiftBarプラグインにおけるクリック一つの多言語切り替え（i18n）アーキテクチャ

### 事象
メニューバーの表示文言がハードコーディングされた日本語のみであったため、英語圏ユーザーには使いづらく、グローバル展開に不向きだった。

### 対策
- **`MESSAGES` 辞書パターン**: スクリプト先頭にキー付きの多言語メッセージ辞書 `MESSAGES = {"en": {...}, "ja": {...}}` を定義し、すべてのUI文字列を辞書からの参照に切り替えた。
- **`--set-lang` コマンドライン引数**: ドロップダウンの言語選択UIクリック時に `bash` パラメータ経由で `--set-lang en` または `--set-lang ja` を実行し、`quota_cache.json` にユーザー設定を永続化する設計とした。
- **チェックマーク `[✓]` による現在言語の可視化**: 現在選択されている言語にのみ `[✓]` を表示し、直感的に現在のモードを伝えるUI設計にした。
- **`format_reset_time(iso_str, lang)` への `lang` 引数の追加**: リセット時間表示（`reset` vs `リセット`）も含めて全テキストを言語に応じて動的に出し分ける完全な対応を実現。

### 教訓
- SwiftBarのようなメニューバーツールで多言語対応を行う際は、**ドロップダウンメニュー内に言語選択UIを組み込み、クリック一つでキャッシュファイルに書き込む `--set-lang` パターン**が、設定ファイルの手編集を不要にするシームレスな手法として極めて有効。
- ハードコーディングされた文字列を後から多言語化する際は、「辞書 + `msg = MESSAGES[lang]` パターン」で**すべての文字列参照を一箇所に集約**し、今後の言語追加（例：中国語、韓国語）にも1辞書ブロックの追加だけで対応可能な拡張性を確保すること。
- テストコードにおいては、**言語ごとに個別のテストケースを用意**し、英語テスト・日本語テストをそれぞれ独立したアサーションで検証することで、意図しない表記混在バグを完全に防止できる。

## 12. gRPC-Web (proto3) JSONシリアライズにおけるクォータ0%（デフォルト値）フィールド欠落バグと、lsofのPID指定によるディレイ解消

### 事象
- クォータが0%になったモデル（Claude Sonnet/Opusなど）が、タスクバー上（SwiftBar）で `0%` ではなく `100% (🟣)` と表示されるバグが発生。
- IDE側のModels画面とステータスバー表示の間にディレイ（タイムラグ）があり、0%への反映が遅れる問題があった。

### 原因
1. **gRPC-Web / proto3 のシリアライズ仕様**: クォータが消費されて0%になった際、APIレスポンス（Connectプロトコル）内の `remainingFraction` フィールドの値が `0`（デフォルト値）になります。proto3の仕様では、数値型のデフォルト値（`0` または `0.0`）はJSONシリアライズ時に**フィールドごと省略**されます。従来のスクリプトでは「フィールドが無い場合はクォータに問題がない（100%）」と解釈していたため、0%になったモデルが100%と誤判定されていました。
2. **lsofのシステム全体スキャンによる遅延**: LSPプロセスのポートを特定する際、`lsof -i -P -n` を実行していましたが、システム全体の全ネットワークソケットをスキャンするため実行時間が数秒以上かかり、SwiftBarのタイムアウト制限（10秒）を引き起こしていました。このため、キャッシュが古い値（20%など）のままフォールバックされ続け、表示に大きなディレイが発生していました。

### 対策
- **欠落フィールドの0%解釈**: `quotaInfo` オブジェクトが存在するにもかかわらず `remainingFraction` が省略されている場合、それは「クォータ残量 0 (0%)」とみなすように `get_quota.js` の判定ロジックを修正。
- **lsofの特定PID絞り込み**: `lsof -a -p ${pid} -i -P -n | grep LISTEN` のように `-p` オプションで対象のLSPプロセスIDを直接指定し、ソケット探索を一瞬（10倍以上高速）で完了するように改善。

### 教訓
- gRPC や Protocol Buffers (proto3) を用いるAPIをリバースエンジニアリングする際、**「数値が 0 (デフォルト値) の場合はフィールド自体がJSONから消滅する」**というシリアライズ仕様を念頭に置いて判定ロジック（`undefined`の扱い）を実装しなければならない。
- `lsof` などのシステムリソーススキャンコマンドをスクリプトで定期実行（ポーリングなど）する際は、スキャン範囲をグローバルにせず、必ず **特定PIDやポートに絞るオプションを指定してスキャンのオーバーヘッドを極小化する** ことが、タイムアウトや動作のディレイを防ぐために極めて重要である。

## 18. APIレスポンスデータの仕様誤認に伴う「リセット時間の常時返却」の罠と、シンプル設計への回帰

### 事象
クォータが正常（満タン / 100%）に機能している場合であっても、メニューバー上の表示がすべて `0% 🔴` に固定されてしまう壊滅的な表示バグが発生した。

### 原因
LSPの Connect API 応答内の `resetTime`（回復時間）フィールドは、**「現在クォータ制限がかかっているかどうかに関係なく、常に次回の定期リセット日時（未来の時刻）を返却し続ける仕様」** であった。
前回の「LSP起動時の同期ラグ（不整合）」を無理に防ごうとして追加した `if (resetTime > now) { remainingFraction = 0; }` という補正ロジックが災いし、満タンで正常なモデルの `resetTime` まで未来を指していることから、すべてのモデルを一律で 0% 🔴 に強制書き換えしてしまった。

### 対策
- 間違った日時補正ロジックを即刻「完全撤去」し、元の「`remainingFraction` が数値型ならそのパーセンテージを採用し、省略時は 0% とする」最も安定したシンプルなロジックへと安全に完全復元。
- 手動テストおよび Python 連携テストを再実行し、正常なモデルが `100%` や `80%` と正しくリアルタイムに描画されることを実証・確認した。
- バージョンは `1.3.7` のまま、手元検証用の `.vsix` パッケージを再ビルドした。

### 教訓
- API から取得した日時情報（`resetTime` など）をトリガーにしてステータスを強制補正する際は、**「正常な時でもその日時は未来を指すのか」という API の静的・動的な仕様（状態遷移）を徹底的に検証・確認** しなければならない。
- 一時的な起動ラグ（一瞬100%に見えて数秒で0%に落ちる現象）のような過渡的な不整合は、時間が解決する軽微なものである。そのため、下手にフロント側で先読み補正をかけて複雑なロジックを組むより、**「元の最もシンプルで頑丈なロジックに任せる（複雑な過剰エンジニアリングを避ける）」** ことが、長期的な安定性と品質を守るための鉄則である。

## 19. アクティブなLSPログの動的切り替えと、会話メタデータからの超高速な承認状態の検出設計

### 事象
- エージェントのステータス（思考中、承認待ちなど）をリアルタイムに検知するシステムバー（SwiftBar）表示の開発において、従来の `daemon/ls_*.log` は一部の起動環境で書き込みが停止しており、実際には `~/Library/Logs/Antigravity/language_server.log` にログが出力されていた。
- また、ログのデバッグレベルや出力タイミングによっては、ユーザー承認待ち（問合せや承認ダイアログ）のトリガーログを正確にフックする難易度が高かった。

### 解決策
1. **ログファイルの動的優先切り替えロジック**: `language_server.log` の有無を最優先でチェックし、フォールバックとして従来の daemon ログや他の IDE ログディレクトリも順次スキャンして最も新しいファイルを動的に特定する設計（`get_latest_log_file`）を導入し、完全な堅牢性を確保した。
2. **会話フォルダのメタデータ連携による承認状態の超高速フック**: `~/.gemini/antigravity/brain/` にある最新の会話フォルダの `*.metadata.json` をパースし、いずれかのファイルに `"requestFeedback": true`（＝ユーザーの入力・承認待ち状態）が立っているかを直接スキャンする判定エンジンを設計した。これにより、ログの記述規則に一切依存しない、100%正確で超高速なフック（誤検知ゼロ）を実現した。

### 教訓
- プロセスの状態を監視する際、単一のログファイルパスのみを固定の監視対象にすると、実行環境やバージョンアップによるパスのズレで壊滅的なバグになりやすい。優先パスを定義しつつ、フォールバックの検索範囲を動的に広げる「自動切り替え設計」にすること。
- また、ログのテキストパースといった不安定で曖昧な手法だけでなく、**「システムやフレームワークがディスクに直接書き出すセッション状態（メタデータやタスク状態のJSONなど）」を並行スキャンすること**が、状態検知の確実性とパフォーマンスを最大化するための極めて強力なアプローチである。

## 20. メニューバーにおける「常時クォータ情報維持 ＆ プレフィックス状態切り替え」UXと、未来時刻ズレによるフック固着バグの回避

### 事象
- エージェントのステータス（思考中や承認待ち）をシステムバーに表示する際、当初はタイトル文字列全体を「思考中...」に切り替える方式にしていたが、ユーザーから「思考中でも現在のモデル別残数値（クォータ）は常に並べて見ていたい」という強力なUX上のフィードバックが発生した。
- また、エージェントが動作を終えて完全にアイドル状態になった後も、システムバーが `🧠`（思考中）のまま元に戻らない（固着する）壊滅的なバグが発生した。

### 解決策
1. **左端アイコンのみの動的プレフィックス統合UI**: 表示情報量を1ミリも犠牲にしないため、通常時のクォータ横並び文字列を完全に残したまま、**一番左側のアイコンのみ**を状態に応じて動的にスワップ（待機中: `👾`, 思考中: `🧠`, 承認待ち: `⚠️`, 停止: `⚪️`）する統合設計へと刷新した。承認待ちの際は、テキスト色オプション（`| color=#ff3b30`）を結合してテキスト全体を赤文字で点灯させるハイライトも統合した。
2. **タイムスタンプのレンジ制限 (`0 <= diff <= 30`)**: システム現在時刻（`now`）とログからパースしたタイムスタンプ（`log_dt`）にミリ秒単位のズレがあり、ログのほうがわずかに未来を指していた場合、差分秒がマイナス（負の値）になってしまい、従来の `diff <= 30` 判定では未来時間もすべて「30秒以内」と判定されて「思考中が永久に解除されない」バグになっていた。これを防ぐため、下限値を設けた `0 <= diff <= 30` という厳密なレンジ制限に修正した。
3. **ログ更新停止（`mtime`）との連動前提条件**: ログファイル自体の最終更新日時（`mtime`）が現在時刻から15秒以上前（＝LSPからのログ書き込みがストップしている状態）であれば、自動的に `is_thinking = False` と判定する防護設計を組み込んだ。

### 教訓
- メニューバーのように限られた領域でステータスを可視化する際、「画面の完全切り替え」は重要な監視データ（クォータ残量）を一時的に隠蔽してしまうため、UXの観点からは悪手になりやすい。**「ベースとなる監視テキストは常時維持したまま、左端のステータスアイコンのみを動的に変化させる統合アプローチ」**が、高い情報量とリアルタイム状態把握を両立する最もプロフェッショナルでプレミアムな設計である。

## 21. 非干渉な太いデリミタ `❘` によるUI分割の明示と、秒数ハックに基づくバグゼロな動的交互アニメーション設計

### 8. SwiftBarにおけるパラメータパースの脆弱性とインデントの消失
**問題**: `| font=sans-serif size=12 bold=true` のように、SwiftBarでサポートされていないプロパティ（`bold=true`など）をパラメータ文字列に含めると、SwiftBarはその行のパラメータ全体（`color`など）をパースエラーとして**無音で完全に無視**してしまう。また、メニュー行の先頭にある通常の半角スペースはSwiftBarによって自動的にトリム（削除）されるため、意図した字下げ（インデント）が失われ、UIのレイアウトが崩壊する。
**解決策**: サポート外のプロパティ（`bold=true`等）は絶対に使用しないよう修正。また、字下げを確実に行うため、通常の半角スペースの代わりに**Non-Breaking Space（`\u00A0`）** を用いることで、トリムを回避し美しいインデントを維持した。

### 9. urllibにおけるProxy汚染とAPIフォールバック（ハードコード値）のサイレントバグ
**問題**: SwiftBar経由で実行された際、Pythonの `urllib.request.urlopen` が意図せずシステムのプロキシ環境変数を拾ってしまい、127.0.0.1へのAPIリクエストが失敗し続ける現象が発生。さらにAPI取得に失敗した際に、開発時にテスト用として `DEFAULT_QUOTAS` にハードコードした `P-Low: 40` が恒久的に表示され続け、「特定のモデルだけ常に40%で連動しない」というユーザーを混乱させる重大なバグを引き起こした。また複数の言語サーバー（IDEやHub）が混在していると、間違ったHTTPSポートを引き当ててエラーになるケースもあった。
**解決策**: 
1. `urllib.request.ProxyHandler({})` を明示的に設定し、プロキシを無効化して確実にローカル通信を通すようにした。
2. 存在する全言語サーバーの全ポートを総当たりでチェックし、成功するまで試行する堅牢なフェッチロジックに改修した。
3. `DEFAULT_QUOTAS` の仮のハードコード値をすべて `100` にリセットし、誤解を招く数値を徹底排除した。
4. エラーの握り潰し（`pass`）をやめ、取得失敗時は `/tmp/agq_error.log` にログを残すようトレーサビリティを確保した。

### 9. urllib.request における HTTPS/Proxy 干渉と複数言語サーバー問題
**問題**: ユーザー環境において `fetch_quota_from_api` が常に失敗し、ダミーの初期キャッシュ値（`P-Low: 40%`等）が表示され続けるバグが発生した。原因は3つ。
1. `urllib` がシステムプロキシ環境変数を自動参照し、127.0.0.1へのリクエストが失敗していた。
2. Antigravity の `language_server` は IDE用と Hub用の複数プロセスが存在し、それぞれ異なるポート（HTTPS/HTTP）を開いている。スクリプトがIDE用のHTTPSポートにHTTPリクエストを送信すると `400 Bad Request` で失敗していた。
3. 初期ダミー値としてテスト用の `40%` がハードコードされていたため、ユーザーから「1つだけ40%で連動していない」と誤解を招いた。
**解決策**:
- `urllib.request.ProxyHandler({})` を設定し、プロキシを無効化した。
- `find_lsp_info` を完全に書き換え、**すべての** `language_server` プロセスをリストアップし、それぞれのプロセスがリッスンしている**全ポート**を抽出するようにした。そして成功するまで全ポートに対してフェッチを試行する堅牢なループへ変更。
- ハードコードされていたダミー値（40%）をすべて 100% に修正し、万が一フェッチに失敗しても不自然に見えないようにした。
   - **承認待ち (`pending`)**: `⚠️ 承認待ち` ➔ `💬 入力要求` (多言語対応) を5秒ごとに赤点滅。
   - **待機中 (`idle`)**: `👾` ➔ `✨` が5秒ごとに煌めくように交互切り替え。
   これらをファイル保存や永続化処理を一切使わずに、完全にバグゼロで滑らかに動作させることに成功した。
3. **余計なインデント記号の完全排除**: ドロップダウン内の `▸` などの余計な記号を完全に廃止し、クリーンな4スペースインデント（`    `）に統一。

### 教訓
- メニューバーにおける表示分割には、プラットフォームの予約デリミタ（`|` など）との競合を避けつつ、見た目の美しさと論理的分割を高レベルで満たすUTF-8非予約系記号（U+2758 `❘` や U+2016 `‖` など）を選択するのが鉄則である。
- 定期実行型のウィジェットやプラグインで「アニメーション」を実現する際は、状態をファイル等に保存して永続化するアプローチ（壊れやすい）を避け、**「システムクロック（現在時刻 of second）から周期サイクルを算出するステートレス設計」**を採用することで、バグを完全に排除し、極めて軽量かつ安定したアニメーションを実装することができる。

## 22. Streamable（常駐ストリーミング）プラグインにおける「ファイル名への更新間隔（時間指定）必須」仕様と自動クリーンアップの罠

### 事象
AQM を Streamable（常駐ストリーミング）プラグインへ移行し、VS Code 拡張機能パッケージ（V1.5.0）をインストールして SwiftBar を再起動した際、古い `antigravity_status.1s.py` などは消え去ったが、メニューバー上の表示が完全に消えて出なくなってしまった。

### 原因
1. **SwiftBar のファイルスキャン仕様（時間指定必須）**: SwiftBar（および xbar）は、プラグインディレクトリ内のファイルをスキャンする際、**「ファイル名に更新間隔の指定（例：`.5s` や `.30s`）が含まれていないファイル（例：`antigravity_status.py`）はプラグインとして認識せず、完全にロード対象外として無視する」**という内部仕様を持っていた。
   - ストリーミング（`streamable`）モードにする場合であっても、ファイル名自体には `{name}.{time}.{ext}`（例：`antigravity_status.5s.py`）という時間指定が必要である。
   - プラグイン内部に `# <swiftbar.type>streamable</swiftbar.type>` が記述されていれば、SwiftBar は起動後に「常駐モード」を認識してファイル名の更新間隔を無視し、無限ループ内のストリームプッシュ（`~~~`）のみに同期するようになる。
2. **手動配置ファイル名の残留競合**: ユーザー環境に手動で作成された `antigravity_status.1s.py` が残っていたため、中身が無限ループであるのに対し、SwiftBar が1秒ごとに重複起動しようとしてハングアップを引き起こしていた。

### 対策
- **`extension.js` でのクリーンアップ対象の最適化**:
  `filesToCleanup` リストに、時間指定のない無効な `'antigravity_status.py'` や、古い `'antigravity_status.1s.py'` などを追加して自動的に綺麗に消去する。
- **時間指定付きの正しいファイル名での展開**:
  コピー先のファイル名を `antigravity_status.5s.py`（または `.10s.py` など）に設定する。ストリームが万が一クラッシュした際のフォールバック周期としても `5s` が最も安定している。
- **プロセスの完全一掃と再起動**:
  古い重複プロセスを `pkill -f antigravity_status` でメモリから一掃し、`killall SwiftBar` を経て SwiftBar を再起動する。

### 教訓
メニューバー統合ユーティリティにおいて、定期実行型から常駐ストリーミング（streamable）型へアーキテクチャを刷新する際は、**「常駐型であっても、プラットフォーム側がプラグインとしてスキャンして起動するためには、ファイル名に更新間隔（時間指定）を含める規則が必須である」**という内部仕様を絶対に忘れてはならない。
これを怠って単に時間指定のないクリーンなファイル名（`status.py` 等）で配置すると、プラットフォームから完全に無視されて起動すらされなくなる。
デプロイ設計時には、**「ファイル名にはフォールバック用の時間指定（`5s` 等）を維持し、内部メタデータで常駐ストリーミングをONにし、過去の無効ファイル（`status.py` や `1s.py`）をすべて自動削除クリーンアップする」**という多重防護デプロイロジックの構築が極めて重要である。

## 22. メニューバー溢れによる表示制限バグの回避と、SwiftBar 終了後の plist 強制書き換えシーケンス

### 教訓

## 23. ワークスペースなし起動時の VS Code 拡張機能アクティベーション停止問題と、再インストール時のキャッシュバグの完全回避

### 事象
V1.5.0 を VSIX から再インストールし、ウィンドウをリロードしても拡張機能が起動せず、SwiftBar へのスクリプトデプロイやリフレッシュ再起動が一切動かない不具合が発生した。

### 原因
1. **ワークスペース未選択時のアクティベート制限**: `package.json` で指定していた `"activationEvents": ["onStartupFinished"]` は、VS Code がフォルダ（ワークスペース）を開かずに起動された場合、環境やバージョンによっては発火が著しく遅れる、または発火自体が停止してしまうバグが存在する。

1. **常時アクティベート仕様（`"*"`）への堅牢化**:

2. **キャッシュを完全破棄させるためのバージョンバンプ（`1.5.1`）**:

### 教訓
開発段階やバグ修正段階において「同一バージョンでのインストール確認」を繰り返すと、VS Code の内部キャッシュバグにより「修正したはずのコードが実際には反映されていない」という深刻な誤認・迷宮入りに陥るリスクが極めて高い。VS Code 拡張機能の重大な修正やアクティベーションイベントの調整を行った際は、**「絶対にバージョンを1つ以上バンプしてビルドすること（例: 1.5.1）」** および **「ワークスペース未選択状態でも確実に動かすために activationEvents を * にすること」** を徹底することが、デプロイバグを100%防止し一撃で確実な復帰を勝ち取るための鉄則である。

## 25. メタデータファイルの永続性とログ末尾走査によるステート検出の優位性

### 事象

### 教訓

## 28. 非同期キャッシュフェッチ時のユーザー設定維持バグ

### 事象
言語設定を「日本語」に変更しても、バックグラウンドでの非同期フェッチ（`do_bg_fetch`）が走った直後（5〜15秒後）に、強制的に「英語」に戻ってしまう不具合が発生した。

### 原因
非同期でAPIデータを取得して `quota_cache.json` に保存する際、言語設定キー `"language": "en"` を常にハードコードして上書きしていたため、UI操作で書き換えられた値が非同期プロセス側で消去されてしまっていた。

### 対策
キャッシュ書き込みを行う前に、既存のキャッシュから `language` 設定をロードして引き継ぐ（マージする）ように修正した。
```python
cache_data = load_quota_cache_data()
lang = cache_data.get("language", "en")
save_quota_cache_data({
    ...,
    "language": lang
})
```

### 教訓
非同期タスクや別プロセスで共通のキャッシュ・設定ファイルを更新する際は、一部のフィールドだけを更新する場合であっても、絶対に他の既存フィールド（特にユーザーの設定値）をデフォルト値やハードコード値で破壊的に上書きしてはならない。必ず既存データをロードして引き継ぐか、差分マージ（`dict.update`等）を行う設計を徹底すること。

## 29. モックフラグの残存と is_cached の動的判定

### 事象
APIから最新データが正常にリアルタイム同期されているにもかかわらず、メニューバーやドロップダウン表示に永久に `(cached)` や `（キャッシュ表示中）` という表示が残り続けていた。

### 原因
開発中のデバッグや一時的な動作保証のためにメインループで `is_cached = True` という静的なフラグがハードコードされたまま本番実装に残っていたため。

### 対策
最後にバックグラウンドフェッチが成功した時刻（`last_fetch_time`）のタイムスタンプと、現在時刻の差分を動的に算出し、`interval + 5秒` 以内（＝同期タスクが順調に動いている）であれば `is_cached = False` (リアルタイム同期中)、それを超えていれば `is_cached = True` (キャッシュ表示中) と判定する動的なロジックへ修正した。
```python
is_cached = (time.time() - last_fetch) > (interval + 5)
```

### 教訓
開発やデバッグのために一時的にコード内に埋め込んだハードコード（モック用フラグ等）は、本番リリース前に必ず検出し、動的な判定式に置き換えることを徹底する。また、テストコードにおいてもこの動的な判定が正しくアサーションされるか確認するテストケースを設けること。

## 30. ユニットテスト実行時の stderr リダイレクト問題の回避

### 事象
ユニットテスト（`test_status.py`）を実行した際、テストに失敗しているにもかかわらずコンソール出力が完全に空（Stdout/Stderrともに空）で終了コードだけが1になるため、デバッグが極めて困難になる問題が発生した。

### 原因
検証対象の `antigravity_status.py` をインポートした時点で、プロダクションコード内のデバッグ用処理 `sys.stderr = open('/tmp/agq_crash.log', 'w')` が強制発火し、`unittest` がコンソールに出力するはずのエラーやトレースバックがすべてファイルへ流れてバッファリングされていたため。

### 対策
テストコード（`test_status.py`）のインポート部で、インポート中だけ `sys.stderr` を退避し、インポート直後に元のコンソール出力へ復元するガード処理を実装した。
```python
original_stderr = sys.stderr
import antigravity_status
sys.stderr = original_stderr
```

### 教訓
プロダクションコードで `sys.stderr` や `sys.stdout` のリダイレクトを伴うモジュールを単体テストする際、テストスイート自体の出力機能が損なわれるリスクがある。テストコードのセットアップ部でこれらを退避・復元するか、モックを活用してテスト出力が常にコンソールへ正常表示されるように防護設計を行うこと。

## [2026-06-13] 単体テスト・連結テスト・表示の総合テストの自律的計画および徹底検証ルール
**問題:** 開発プロセスにおいて、テストを明示的に行わずにリリースやデプロイを行ってしまうと、Y軸目盛りの重複や表示アニメーションの不整合、競合といったバグが本番環境で発生してしまう。

1. **単体テスト (Unit Test)**: 新規および変更された関数・ロジックの入出力に対する検証。特に境界値（例: 0%や100%のケース、差が極小のケース、計算式でゼロ除算が発生しうるケース）のエッジケースに対するテストを個別にコードレベルで実行する。

**原則:** 「動作検証を行わずに提出しない」ことを絶対の掟とする。テスト手法や計画（単体/連結/総合の3種）を開発前に `task.md` または `implementation_plan.md` に明記し、すべての検証結果ログやキャプチャで安全を証明した後に完了とすること。
